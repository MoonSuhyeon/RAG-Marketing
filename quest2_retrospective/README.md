## 1단계: 기본 구조 만들기

- Layered Architecture 설계
    
    : RAG / API / UI 3개 레이어로 분리 (RAG·UI 레이어 간 상호 영향 없이 독립적 수정 가능)
    
    - RAG 레이어(rag_engine.py) : 검색/생성 비즈니스 로직 담당
    - API 레이어(server_api.py)  : HTTP 인터페이스 담당, 라우터 조립
    - UI 레이어(client_app.py) : 사용자 화면 담당, API 호출만 수행
- Config 중앙화
    
    : 환경별 설정을 통합 관리하여 변경 비용 최소화
    
- JWT 인증 구조 설계
    
    : 사용자 인증 및 접근 제어 기반 마련
    
    - Q. JWT 인증 구조가 뭔가요?
        
        "JWT 인증 게이트는 시스템의 API를 보호하기 위해 사용자의 신원을 검증하는 보안 계층입니다.
        
        JWT(JSON Web Token)라는 표준화된 토큰을 사용하여, 인가된 사용자만 RAG API에 접근할 수 있도록 통제합니다. 단순히 로그인을 했는지뿐만 아니라, 토큰 내부에 포함된 '권한 정보(Role)'를 확인하여 일반 사용자인지, 시스템 관리자인지를 구분하여 접근 권한을 세밀하게 제어할 수 있습니다.
        
        이를 통해 부적절한 호출을 사전에 차단하고, 서버 리소스를 안전하게 보호하는 역할을 합니다."
        
- Rate Limiting 정책 정의
    
    : 사용자별 요청 한도(사용자 ID 기준 시간당 20회) 정의, 초과 시 HTTP 429 반환으로 요청 차단 (OpenAI API 비용 급증 방지 + 서버 과부하 방지)
    
- Logging / Monitoring 설계
    
    : 시스템 상태 추적 및 장애 대응 기반 구축 (설계만 먼저 하고, 구현은 이후 단계에서 점진 적용)
    
    - 평가 로그 탭에서 정확도, 관련성, 환각 개별 기록
    - 메트릭 탭에서 평균 정확도, 실패 유형 분포, 응답 지연, 서버 상태, 인덱스 집계
    - Trace Spans 서브탭에서 단계별 토큰 사용량, 단계별 소요 시간 기록

## 2단계: 검색 기능 만들기

- Embedding 기반 벡터화
    
    :  `text-embedding-3-small` (OpenAI) — 비용 대비 성능 우수, 동일 API 키로 통합 관리

- GPT 기반 Answer Generation
    
    :  `gpt-4o-mini` — 저비용으로 한국어 답변 품질 확보

## 3단계: 성능 측정하기

- LLM 자동 평가
    
    : overall_score = (정확도 + 관련성) / 2 - 환각 패널티
    
    - 평가 로그 탭에서 정확도, 관련성, 등급, NDCG@k, Reranker Gain, 검색 품질, 병렬 검색을 확인할 수 있음
    - Q. RAG 답변 평가 기준에서 등급은 어떤 기준에 따라 산정되나요?
        
        "현재 등급 산정은 자체 제작한 LLM 채점 방식을 기반으로 합니다. 답변 생성 후 LLM이 정확도와 관련성을 1점에서 5점으로 실시간 채점하고, 여기에 환각 패널티를 차감한 Overall Score로 A부터 F까지 등급을 산정합니다.
        
        다만 객관성을 높이기 위해 RAGAS 라이브러리도 병행 적용했습니다. Faithfulness, Answer Relevancy, Context Precision 3개 지표를 별도로 축적하고 있으나, RAGAS는 매 질문마다 실행하면 응답 지연이 크게 증가하기 때문에 현재는 오프라인 별도 실행 방식으로 분리해두었습니다.
        
        향후에는 비동기 처리나 배치 평가 방식을 도입하여 RAGAS 결과도 Streamlit 대시보드에서 실시간으로 확인할 수 있도록 개선할 계획입니다."
        
    - Q. NDCG@k는 어떤 의미를 가지며, 
    이를 기반으로 검색 품질 탭에서 여러 지표를 함께 제공한 이유는 무엇인가요?
        
        “NDCG@k는 검색 결과 상위 k개에서 관련 문서가 얼마나 상위에 잘 배치되어 있는지를 평가하는 지표입니다. 여기서 k는 평가에 포함할 “상위 k개의 검색 결과 범위”를 의미합니다.
        
        이 지표는 각 문서의 관련성 점수를 단순히 더하는 것이 아니라, 순위가 낮을수록 점수를 감소시키는 방식으로 합산(Discounted Cumulative Gain)한 뒤, 이를 이상적인 정렬 결과와 비교해 0~1 사이로 정규화한(Normalized) 값입니다.
        
        즉, 관련성 높은 문서가 상위에 많을수록 점수가 높아지며, 이를 통해 해당 검색 결과가 얼마나 잘 정렬되었는지를 나타냅니다.”
        
        “검색 품질 탭에 NDCG@k와 다른 3개 지표를 함께 둔 이유는, 하나의 수치만으로는 검색 성능을 실무적으로 해석하기 어렵기 때문입니다.
        
        검색 → 개선 → 해석 → 성능의 전체 흐름을 기준으로 나누어, Reranker Gain은 개선 효과를, 검색 품질 라벨은 직관적 해석을, 병렬 검색(ms)은 실제 서비스 속도를 나타내도록 구성했습니다.
        
        이를 통해 검색 성능을 정밀도, 개선 효과, 직관성, 속도 4가지 관점에서 동시에 판단할 수 있도록 설계하였습니다.”
        
- Token 사용량 측정
    
    : 각 질문 처리 시 소비된 토큰을 단계별로 기록하여 API 비용 추적
    
    - Trace Spans 서브탭에서 단계별 토큰 확인 가능
    - 총 토큰은 Trace Spans 상단 카드에서 확인 가능
- Latency 측정
    
    :  각 질문 처리 시 소요된 응답 시간을 기록하여 속도 성능 지표 확보
    
    - 메트릭 탭 > 응답지연 섹션에서  P50, P95, P99, 평균 확인 가능
    - 총 지연은 Trace Spans 상단 카드에서 확인 가능
        - Q. P50, P95, P99, 평균이 의미하는 게 뭔가요?
            
            “전체 응답 속도 분포를 백분위로 나타낸 성능 지표입니다.
            
            P50은 사용자 절반이 겪는 중앙값이고, P95와 P99는 느린 소수(하위 5%, 1%)의 경험을 나타내는 지표입니다. 평균은 전체 응답 시간의 산술 평균으로, 전반적인 속도 수준을 파악하는 데 활용됩니다.
            
            평균에 가려진 최악의 지연 시간을 모니터링하여, 모든 사용자가 특정 임계치 안에서 안정적인 서비스를 받을 수 있도록 관리하기 위해 활용합니다."
            
- Tracing
    
    : 질문 하나가 시스템을 통과하는 내부 흐름을 단계별로 기록
    
    - 상세 분석 > Trace Spans 서브탭에서  소요시간, 토큰, 입력 요약, 출력 요약, 판단 근거를 추적할 수 있음

## 4단계: 검색 정확도 높이기

- Semantic Chunking + Overlap
    
    : 문맥 유지
    
    - 사이드 슬라이더를 통해 청크 크기와 오버랩을 설정할 수 있게 함
    - Q. 문맥 단절 제거 어떻게 하나요?
        
        “청킹 자체가 1차 단절 지점이라서, 50자 오버랩을 기본으로 두고 경계 정보 손실을 막았습니다. 더 나아가 문장 임베딩 유사도가 급락하는 지점에서만 자르는 의미론적 청킹 옵션을 넣어, 의미 경계에서만 분할되게 했습니다.”
        
- Hybrid Search (BM25 + Dense) & RRF
    
    : 검색 누락 최소화 (Recall 향상) & 검색 결과 통합
    
    - 사이드 콤보박스를 통해 Hybrid 또는 Dense 또는 BM25를 선택할 수 있게 함
    - Q. BM25에 대해 설명해 보세요. TF-IDF와 뭐가 다르죠?
        
        “BM25는 정보 검색 분야에서 가장 널리 쓰이는 알고리즘 중 하나로, 특정 쿼리에 대해 문서의 관련성을 점수로 계산해 순위를 매기는 방식입니다.
        문서 내 단어 빈도(TF)뿐만 아니라, 그 단어가 전체 문서군에서 얼마나 흔한지(IDF)를 고려하며, 특히 문서의 길이에 따른 가중치를 조절해 공정한 점수를 부여합니다.
        BM25와 TF-IDF는 모두 키워드 빈도를 측정하지만, BM25는 TF-IDF의 한계를 극복한 진화형입니다.
        
    - Q. Dense Search가 뭔가요? Dense Search의 반대 개념과 함께 설명해 보세요.
        
        “Dense Search는 텍스트를 고차원 벡터로 변환하여 문맥적 의미를 검색합니다.
        
        Dense Search의 반대 개념인 Sparse Search는 단어의 등장 여부를 0과 1 또는 빈도로 표시하는 고전적 방식입니다. 키워드가 정확히 일치해야 합니다. BM25가 대표적인 Sparse Search 모델입니다.”
        
    - Q. 재현율(Recall) 향상은 어떻게 하나요?
        
        “재현율은 질문에 필요한 정보를 하나도 놓치지 않고 다 가져오는 능력을 의미합니다.
        
        Hybrid Search를 통해 BM25(키워드)와 Dense Vector(의미) 검색을 동시에 수행하여, 고유명사 검색 누락과 문맥 이해 부족을 동시에 보완하였습니다.”
        
    - Q. RRF에 대해 설명해 보세요.
        
        “서로 다른 검색 엔진이 가져온 결과들을 하나의 통합 순위로 합치는 알고리즘입니다.
        
        하이브리드 서치가 "키워드 기반 검색(BM25)과 의미 기반 검색(Vector)의 장점을 섞어서 쓰자!"라는 방법론이라면, RRF는 "키워드 검색 결과와 벡터 검색 결과가 각각 나왔는데, 이걸 어떤 기준으로 합쳐서 최종 순위를 매길까?"에 대한 수학적 해답입니다.
        
        서로 다른 점수 체계를 가진 결과물들을 단순 점수가 아닌 순위의 역수를 취해 합산하여 
        서로 다른 스코어 단위를 가진 지표들을 공정하게 통합할 수 있습니다.”
        
- Query Rewriting
    
    : 검색 의도 명확화 (Recall, Precision 향상)
    
    - 사이드 체크박스를 통해 활성화
    - Q. 쿼리 재작성 프로세스에 대해 설명해 보세요.
        
        “쿼리 재작성은 불완전한 사용자 질의를 검색 최적화 상태로 가공하는 고도화 메커니즘입니다.
        
        먼저 질의를 상위 개념으로 추상화(Step-back)하여 광범위한 맥락을 확보하고, 이를 다양한 관점으로 다각화(Multi-query)함으로써 검색의 사각지대를 해소합니다. 여기에 가상의 답변 형태(HyDE)로 질의를 변환하여 벡터 공간 내 의미적 유사도를 정밀하게 매칭시킨 뒤, 최종적으로 복합적인 요구사항을 단일 의도로 원자화(Decomposition)하여 검색 효율을 극대화하는 흐름으로 작동합니다.”
        
- Reranking
    
    : 상위 후보 재정렬 (Precision 향상)
    
    - 사이드 슬라이더를 통해 Pre-filter N(Reranking 전 후보 청크 수), Top-K(Reranking 후 최종적으로 답변에 사용할 청크 수)을 설정할 수 있게 함
    - Q. 정밀도(Precision) 향상은 어떻게 하나요?
        
        “정밀도의 핵심은 노이즈 제거입니다.
        
        Reranking을 통해 초기 검색으로 가져오는 문서를 Cross-Encoder 모델로 재정렬하여, 최상위 k개 문서의 정답 밀도를 높입니다.”
        
- Ablation Study
    
    : 각 검색 구성 요소 ON/OFF 자동 실험으로 기여도 수치화
    
    - Q.  Ablation Study가 뭔가요?
        
        “시스템을 구성하는 각 요소(Query Rewriting, Reranking, Hybrid Search 등)를 하나씩 제거하거나 변경하면서, 전체 성능이 어떻게 변하는지를 비교하는 실험입니다.
        
        이를 통해 각 구성 요소가 검색 품질이나 성능에 얼마나 기여하는지를 정량적으로 분석할 수 있습니다.”
        
    - Q. 왜 RAGAS를 함께 다루지 않았나요?
        
        “Ablation Study는 검색 구조의 기여도를 분석하는 단계이기 때문에 NDCG, Recall, Latency와 같은 retrieval 중심 지표를 기준으로 성능 변화를 측정합니다.
        
        RAGAS는 retrieval 이후 생성된 최종 답변의 품질을 평가하는 end-to-end 지표이기 때문에 별도의 평가 단계에서 관리됩니다.”

## 5단계: 검색 결과 정교하게 만들기

- Multi-Vector Index
    
    : chunk_index(청크 전체 단위 검색) / sent_index(문장 단위 검색) / kw_index 키워드 단위 검색
    
    - Q. Multi-Vector Index 가 뭔가요?
        
        ”멀티벡터 인덱스는 검색 누락을 최소화하기 위한 전략입니다.
        
        긴 청크는 질문 핵심어가 묻히기 쉬운데,
        
        이를 '요약문', '세부 문장', '키워드' 등 여러 개의 벡터로 쪼개어 인덱싱합니다.
        
        이후 질문이 들어오면 이 벡터들을 병렬로 검색하여, 청크 단위에서 놓친 정보를 정교한 하위 단위에서 보완하여 잡아낼 수 있습니다.”
        
- Context Compression
    
    : 불필요 문장 제거 (압축)
    
    - 임베딩 기반 압축: 통계적 유사도를 기준으로 관련 없는 문장을 고속으로 선별 제거
    - LLM 기반 압축: LLM이 문맥을 직접 추론하여 정보 가치가 높은 핵심 문장만 ID 단위로 추출
    - 사이드의 체크박스를 통해 두 가지 압축 방식을 유연하게 선택하게 함
    - 사이드 슬라이더를 통해 중복 제거 임계값을 설정할 수 있게 함
    - 상세 분석 > 압축 통계 서브탭에서 압축률(ratio)을 확인할 수 있음

## 6단계: 답변 품질을 높이기

- Source Attribution
    
    : 출처 기반 신뢰성 확보 (벡터DB에 각 청크를 메타데이터와 함께 저장해두고, 검색 시 가져와 프롬프트로 인용을 지시)
    
- Self-Refinement
    
    : 초안(Draft)을 스스로 검토(Critique)해서 더 나은 답변으로 개선(Refine)
    
    - 사이드의 체크박스를 통해 활성화함
- Multi-document Reasoning
    
    : 단일 문서로는 답할 수 없는 질문에도 완성된 답변 생성(여러 문서를 각각 요약 후 종합)
    
    - 사이드의 체크박스를 통해 활성화함

## 7단계: 자동으로 고치는 구조 만들기

- Fallback
    
    : 정확도 < 3 또는 환각 감지 시 자동으로 파라미터 바꿔 재검색
    
    - 평가 로그 탭의 fallback 란에서 fallback 발생 여부와 재시도 횟수를 확인할 수 있음
- Cache
    
    : Answer(디스크), Query 결과(메모리), Embedding(pickle), Rewrite(세션), 총 4계층 캐시 (반복 질문 응답 속도·비용 감소)
    
- Failure Classification
    
    : 실패 유형 분석 (환각, 낮은 정확도, 낮은 관련성, 검색 실패, 누락 정보)
    
    - 메트릭 탭에서 실패 유형 분포별 건수 시각화함
- Fine-tuning Dataset 생성
    
    : 학습 데이터 확보 (사용자 질문, 생성 답변, 실패 유형, 평가 결과, 검색 모드, 품질 등으로 구성)
    
    - 사이드 체크 박스를 통해 실패 케이스 자동 저장, 개선 힌트 자동 생성을 실행하게 함
    - 메트릭 탭에서 총 실패 횟수 기록함
    - Q. 실패 학습 루프에 대해 설명해 보세요.
        
        “실패 학습 루프는 RAG 시스템에서 발생한 오답 로그를 구조화하여 분석하고, 이를 학습 가능한 데이터셋으로 변환하는 선순환 구조입니다.
        
        먼저 `classify_failure_types()`를 통해 실패 유형을 자동 분류하여 어떤 단계에서 문제가 발생했는지 가시화합니다.
        
        이후 해당 로그는 failure dataset으로 저장되며, 이 중 학습 가치가 높은 데이터는 별도로 선별하여 fine-tuning 또는 retrieval 개선에 활용할 수 있도록 JSONL 형태로 변환됩니다.
        
        결과적으로 시스템 자체가 즉시 학습하는 구조는 아니지만, 실패 데이터를 지속적으로 축적함으로써 장기적으로 성능을 개선할 수 있는 데이터 중심 개선 파이프라인을 구성하게 됩니다.”

## 8단계: 코드 구조 정리하기

- Layered Architecture  구현
    
    : API 레이어 내부를 기능별 라우터(채팅·문서·메트릭·인증·관리자)로 파일 분리 (각각의 비즈니스 로직이 상호 영향 없이 독립적 수정 가능)
    
    - /chat 라우터(chat.py) : 스트리밍 질의응답
    - /docs 라우터(docs.py) : PDF 업로드 및 인덱싱
    - /metrics 라우터(metrics.py) : 성능 지표 조회
    - /prefix 라우터(admin.py) : 캐시/인덱스 관리
    - /auth 라우터(auth.py) : JWT 인증
    - Q. 왜 처음부터 구조를 나누지 않았나요?
        
        "초기에는 빠른 기능 검증(MVP)이 최우선이었기 때문에 속도에 집중했습니다.
        
        하지만 기능이 확장되면서 코드의 복잡도가 높아지는 것을 방지하고, 장기적인 유지보수와 확장성을 확보하기 위해 Layered Architecture로 리팩토링을 단행했습니다.
        
        이를 통해 비즈니스 로직과 데이터 계층을 분리함으로써, 향후 검색 인덱스나 엔진이 바뀌더라도 기존 로직을 수정할 필요가 없는 유연한 구조를 갖추게 되었습니다."

## 9단계: 속도랑 안정성 개선하기

- 병렬 검색
    
    : 4개 채널(Dense, BM25, 문장, 키워드)을 동시 실행하여 속도 개선
    
    - ThreadPoolExecutor : 스레드 기반 CPU 병렬 처리
    - AsyncRAGEngine : asyncio.gather 기반 I/O 병렬 처리
    - Q. ThreadPoolExecutor 4-way 병렬 검색이 뭔가요?
        
        "ThreadPoolExecutor 4-way 병렬 검색은 네 가지 검색 인덱스를 동시에 조회하여 검색의 정확도와 속도를 동시에 확보하는 구조입니다.
        
        먼저, 사용자의 의도를 완벽히 파악하기 위해 의미 기반의 Dense, 통계 기반의 BM25, 그리고 키워드와 문장 단위 검색을 결합한 하이브리드 방식을 채택했습니다. 이렇게 각기 다른 특성의 인덱스를 활용함으로써 어떤 질문이 들어와도 정답에 가까운 문서를 빠짐없이 확보할 수 있습니다.
        
        하지만 이 4개의 인덱스를 순차적으로 조회하면 응답 지연이 심화되는 문제가 발생합니다. 이를 해결하기 위해 파이썬의 ThreadPoolExecutor를 도입하여 4개의 검색 요청을 병렬로 처리했습니다.
        
        결과적으로 전체 검색 시간은 '네 엔진의 합'이 아니라 '가장 느린 엔진 하나'의 소요 시간으로 단축되었고, 이를 통해 고품질의 검색 결과를 실시간에 가까운 속도로 제공할 수 있게 되었습니다."
        
- Latency 최적화
    
    : Tracing 결과를 활용한 병목 진단
    
- Rate Limiting 적용
    
    : 사용자별로 1시간에 최대 20회 요청 제한, 초과 시 요청 차단
    
- 모니터링 및 Alert 시스템 구축
    
    : 3가지 조건(평균 정확도 < 3.0, 환각 비율 > 30%, P95 지연 > 15,000ms)에서 자동 Alert 발생

## 10단계: AI가 스스로 생각하게 만들기

- Multi-Hop Query Decomposition
    
    : 질문 분해
    
    - Q. 복잡한 질문을 처리하는 'Multi-Hop' 방식의 원리는 무엇인가요?
        
        "Multi-Hop Query Decomposition은 질문을 의미 단위로 쪼개는 Decompose, 각 하위 질문에 대해 순차적으로 정보를 찾는 Hop, 그리고 수집된 정보를 하나로 합치는 Synthesize 과정을 거칩니다. 이를 통해 단편적인 정보 검색을 넘어 다각도의 추론이 필요한 질문에 대해서도 고품질의 답변을 생성할 수 있습니다.”
        
- Self-RAG
    
    : 충분성 판단 후 재검색
    
    - Q. Self-RAG가 뭔가요?
        
        ”Self-RAG는 모델이 자신의 답변을 스스로 모니터링하는 기술입니다. 
        
        답변의 충분성을 판단하고, 부족하면 스스로 검색 힌트를 수정하여 재검색하는 방식입니다.”
        
- ToolRegistry
    
    : 문서 밖 질문 대응 (계산/날짜/웹검색으로 안정성 보완)
    
    - 사이드의 체크박스를 통해 필요시 기능 ON/OFF를 가능하게 함
- Query Routing
    
    : LLM이 질문 의도를 6가지로 분류하고, 복잡도에 따라 전략을 자동 조정
    
    - 단순 질의 (`definition`, `factual_lookup`) → 기본 RAG + BM25/Reranker 가중치 조정
    - 복잡 질의 (`reasoning`, `multi_hop`) → 후보 확장 + MultiDoc 강제, Multi-Hop/Self-RAG와 결합
    - 탐색·불명 질의 (`exploratory`, `ambiguous`) → 넓은 Recall 우선, BM25 부스트
    - 사이드 체크박스를 통해 활성화함
    - Q. 사용자가 라우팅 과정을 볼 수 있나요?
        
        "네, 볼 수 있도록 설계했습니다.
        
        '상세 분석 > 쿼리/라우팅' 서브탭에서 라우팅 의도, 적용된 검색 전략, 재작성된 쿼리를 모두 확인할 수 있습니다.”

## 11단계: 사용자 경험 개선하고 평가하기

- Streaming (SSE)
    
    : 실시간 응답
    
    - Q. 스트리밍이 뭔가요?
        
        "스트리밍은 서버가 답변 전체가 완성될 때까지 기다리지 않고, 생성되는 즉시 한 글자씩 실시간으로 전달하는 방식입니다.
        
        기술적으로는 SSE(Server-Sent Events) 방식을 활용하는데, 이는 서버에서 클라이언트로 데이터를 지속적으로 밀어주는 단방향 통신을 의미합니다. 이를 통해 사용자가 느끼는 첫 응답 시간을 획기적으로 단축하여 훨씬 매끄러운 대화 경험을 제공할 수 있습니다."
        
- RAGAS 평가
    
    : 3개 지표(Faithfulness / Relevancy / Precision) + 종합 평균을 계산해서 수치가 낮으면 청킹/프롬프트/모델을 개선하는 판단 기준으로 활용
    
    - Q. 오프라인 평가와 온라인 평가는 어떻게 다른가요?
        
        "RAG 평가 체계는 객관적 검증과 실전 경험이라는 두 가지 측면에서 오프라인과 온라인으로 나뉩니다.
        
        오프라인 평가가 배포 전 통제된 환경에서 모델의 알고리즘적 성능을 정량화하는 '검증'의 과정이라면, 온라인 평가는 배포 후 실제 환경에서 사용자 만족도와 시스템의 실시간 지연 시간 등을 측정하는 '운영'의 과정이라고 생각합니다."
